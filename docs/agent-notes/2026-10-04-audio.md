# In-app audio: chimes, sync pings, NSDR track (2026-10-04)

Builds on [`2026-10-04-pomodoro-nsdr.md`](2026-10-04-pomodoro-nsdr.md). Replaces the system
sound / `Console.Beep` alert with LTFI's own chimes and plays a local NSDR track in-app.

## What shipped

- **Player abstraction** (`src/LTFI.App/Services/Audio/`): `IAudioPlayer` — `PlayAsync(path)`,
  `PauseAsync`, `ResumeAsync`, `StopAsync`, `SetVolumeAsync(0–100)`, `IsPlaying`, `IsPaused`,
  `CurrentFile`, `PlaybackFinished` (raised on the UI thread). `NetCoreAudioPlayer` wraps
  **NetCoreAudio 2.0.1** (MCI on Windows); NetCoreAudio types don't leave that file. Calls are
  serialised per player, run off the UI thread, and every failure is logged (Serilog) and
  swallowed — tasks never fault, state flags update immediately.
- **Two keyed singletons** (`AudioPlayers.Ambient` for the NSDR track, `AudioPlayers.Notifications`
  for chimes) registered by `services.AddLtfiAudio()` (`AudioServiceCollectionExtensions`, one
  line in `App.axaml.cs`), plus `NotificationSounds` and `AttentionAlert` singletons. Swap the
  backend there.
- **Chimes, synthesised** (`src/LTFI.Infrastructure/Audio/`): `ChimeSynth` is a pure byte
  generator — sines (+ a quiet, fast-fading octave partial for a bell colour), 12 ms linear attack,
  exponential decay to −40 dB, 20 ms release to zero, mixed and normalised to 45 % full scale,
  44.1 kHz 16-bit mono PCM WAV. `Chimes` defines the four sounds and writes them to
  `%AppData%/LTFI/sounds/` (on start-up in the background, and again before each play if a file is
  missing; temp file + move, so a half-written file is never played):
  - `work-done.wav` — C5 → G5 (rising)
  - `break-over.wav` — G5 → C5 (falling)
  - `ping.wav` — single soft E5
  - `nsdr-done.wav` — G4, C5, E5, slow and long
- **AttentionAlert** is now an injected service: `Raise(Chime)` plays the chime and still raises the
  window (restore if minimised, Topmost toggle, Activate). Pomodoro work end → `work-done`; break
  end → `break-over`; NSDR completion (standalone, or in place of a long break) → `nsdr-done`.
  `System.Windows.Extensions` package removed (it only provided `SystemSounds`).
- **Sync pings**: `RemindersPanelViewModel` plays `ping` after a successful sync with
  `Added + Completed + Confirmed > 0` (new reminders, completions, outbox commands confirmed).
  Edits/removals stay quiet. Never on the first background sync (app start-up). The manual SYNC
  button pings too.
- **Settings** (`settings.json`, new `"sounds"` section, `SoundSettings`):
  `soundsEnabled` (true), `soundVolume` (0–100, default 60, clamped), `syncPings` (true).
  `soundsEnabled: false` or volume 0 silences chimes; it does not block a user-configured NSDR
  track. Existing settings files aren't rewritten — add the section by hand to change defaults:
  ```json
  "sounds": { "soundsEnabled": true, "soundVolume": 60, "syncPings": true }
  ```
- **NSDR track**: if `focus.nsdrAudioUrl` is an absolute path (or `file:` URI, env vars expanded)
  to an existing file, starting an NSDR auto-plays it on the ambient player and the panel shows a
  `PLAY AUDIO` / `PAUSE AUDIO` / `RESUME AUDIO` toggle instead of OPEN AUDIO. Any NSDR end — STOP,
  END NSDR, 10:00 reached, session abandoned — stops it (edge-detected in `SyncNsdr`, so every path
  is covered). Track shorter than 10:00 just ends (toggle offers PLAY again, from the top). 10:00
  first → track stopped, then `nsdr-done`. http(s) links keep the OPEN AUDIO (browser) button; a
  bad/missing path also keeps OPEN AUDIO, which explains the problem when clicked.

## NetCoreAudio behaviour (tested on Windows 11)

- `Play` while playing neither stops the old file nor resets its end timer → the wrapper always
  stops first. `Stop` doesn't raise `PlaybackFinished` and does reset the timer. Paused time is
  accounted for (15 s track paused 2 s → finished at 17 s).
- Calls work from any thread; opening an mp3 takes ~250 ms, hence the off-UI-thread queue.
- MCI's `waveaudio` device is **exclusive**: two WAVs on two players can't overlap (the first
  stops; its pause/resume then fail with MCI error 302). An mp3 track (MCI `mpegvideo`) plus a WAV
  chime coexist fine. So `NotificationSounds` **skips a chime while a `.wav` NSDR track is playing**
  (logged); use mp3/m4a for the NSDR track to hear pings during it.
- `SetVolume` uses `waveOutSetVolume` for the process, so it's effectively one volume for both
  players — both use `soundVolume`.

## Verification

- `dotnet build LTFI.sln --no-incremental` — 0 errors, 0 warnings (built to a scratch `OutDir`
  because another agent's running LTFI.App locked `src/LTFI.App/bin`).
- `dotnet test LTFI.sln` — 131 passed. New `ChimeSynthTests` (12): WAV header fields + sample
  round-trip, length = last note + tail, normalised peak with silent start/tail and soft attack,
  440 Hz pitch by zero crossings, empty render, each chime's file name/length, rising/falling
  contours, `EnsureFile` write-once + regenerate-if-missing (no temp left), `sounds` settings
  defaults and camelCase JSON (and files without the section).
- Scratch harness against the built App: DI resolves (ValidateOnBuild) `FocusViewModel`,
  `RemindersPanelViewModel`, two distinct keyed players; chimes written to `%AppData%/LTFI/sounds`;
  a chime played at volume 15 and `PlaybackFinished` cleared `IsPlaying` after the sound.
- App not launched (a parallel agent's work-in-progress migration would have been applied to the
  real database). The NSDR panel bindings are verified by the compiled-binding build only.

## Deferred

- No settings UI for sounds (JSON only); no per-player volume on Windows.
- WAV NSDR tracks silence chimes while playing (MCI limitation above).
- Track position isn't shown; NSDR track doesn't loop.
